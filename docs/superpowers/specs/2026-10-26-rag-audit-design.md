# RAG Audit Workbench：来源审计、源撤回与保护验证

日期：2026-10-26。状态：用户已批准设计与实现；首版交付覆盖里程碑 1，后续能力按各里程碑单独验证。

目标：构建一个可接入现有 RAG / GraphRAG 运行记录的审计工具，并提供无需账户、付费 API 或绑卡的真实撤回回放后端。第三方能够导入证据、核验来源、执行隔离、比较结果、复核报告。

项目定位是工程工具。系统将观察事实、候选解释、干预结果和人工判断分别记录；不预设已经发现新的追溯算法。

## 1. 方案选择

| 路线 | 优点 | 局限 | 决策 |
| --- | --- | --- | --- |
| 审计 SDK + 证据存储 + 回放引擎 + 案件页面 | 可接入既有实验；能实际验证处置；工程深度集中 | 必须处理版本、依赖失效与可重放条件 | 推荐 |
| 纯日志与证据图查看器 | 易部署，接入快 | 无法确认撤回是否生效 | 作为推荐方案的一个模式 |
| 重新训练一个投毒检测器 | 可研究模型效果 | 需要标注、训练和独立泛化评估；难解决派生状态残留 | 不作为本项目主线 |

## 2. 用户与使用场景

主要用户是维护知识库的开发者、研究投毒与追溯的学生，以及需要复核异常回答的审计人员。

一个案件的起点可以是：回答发生异常变化、知识库收到新版本、来源校验失败，或者人工提交一组可疑来源。审计程序不要求先有“确定恶意”的标签。

主流程：

1. 导入或采集源版本、处理产物和一次查询的运行记录。
2. 检查缺失来源、越界原文跨度、过期派生产物、引用断裂和版本不一致。
3. 查看来源到分块、关系、路径、实际上下文和回答的关联。
4. 形成候选撤回集合，列明依据和搜索预算。
5. 在隔离快照中撤回来源，重建受影响状态并重新执行查询。
6. 使用同一剩余源集合从零构建，核验回放的一致性。
7. 比较异常是否缓解、正常查询是否受损，再导出案件报告。

## 3. 接入能力与发布顺序

首个可用版本必须同时包含“导入审计”和“真正执行回放”。默认后端不依赖旧研究环境。

| 接入方式 | 交付能力与阶段 | 明确边界 |
| --- | --- | --- |
| 自带 CPU 文本检索后端 | 摄取文本、分块、构建索引、记录候选与上下文；撤回后真实重建并查询；对照完整重建 | 确定性检索是撤回正确性的验证后端；未接生成器时不报告 LLM 答案恢复 |
| 现有 M4/M5 JSONL | 核验原文跨度、来源与路径；比较已落盘的 baseline/counterfactual | 显示“导入历史结果”，不能当成本次重新执行 |
| 现有规则 GraphRAG 的独立 CPU 适配器 | 第二阶段：语义检索、重新规则抽取、图与路径决策回放 | 新后端单独验证；不得沿用旧 CUDA 实验的验证结论 |
| Microsoft GraphRAG 输出 | 第二阶段：锁定版本的 parquet 导入与血缘检查 | 导入支持不等于具备该系统的源撤回和修复能力 |

默认 CPU 后端采用确定性稀疏检索，固定分词、参数和同分排序。可选本地语义检索适配器使用 BGE-small，模型需锁定具体修订并记录运行设备。未提供模型文件时返回明确的依赖缺失，不静默改换算法。

GraphRAG 的社区摘要、实体合并等环节，只有在对应适配器能提供真实重建能力时才允许标记为“已回放”。缺失环节必须显示在能力清单中。

## 4. 数据与模块边界

采用 Python 包、CLI、本地 SQLite 元数据存储和只读证据文件；页面通过同一应用服务读取案件。首版只支持本地单用户，不扩展为带账号、租户和计费的服务。

| 模块 | 输入 | 主要输出 |
| --- | --- | --- |
| 证据存储 | 文档、版本、运行条件与派生产物 | 内容哈希、版本清单、稳定引用、来源支持集合 |
| 接入 SDK / 导入器 | 处理事件、已保存的记录 | 带版本的统一事件与能力清单 |
| 审计器 | 证据和引用关系 | 可复查的问题清单、严重程度、证据位置和覆盖不足 |
| 回放引擎 | 基线快照、撤回集合、固定查询、运行预算 | 新运行记录、失效与重建清单、完整重建对照 |
| 保护策略 | 来源版本与完整性判定、人工审核记录 | 允许、隔离、拒绝采用、待复核；每项附理由 |
| 案件与报告 | 基线、干预、评估和人工注释 | 可浏览案件、机器可读报告、可验证证据包 |

重要对象包括 SourceRevision、Artifact、Support、Run、RetrievalDecision、ContextSubmission、Intervention、Finding 和 Case。源的逻辑 ID 与内容版本分开；同名文件的新内容不能覆盖旧证据。

来源支持采用多对多集合：同一关系可以由多个文档支持，撤回一个来源时必须保留其他来源的有效支持。重建策略与来源关系不是同一概念，应分别存储。

## 5. 两类追溯证据

**内容血缘**回答“这项内容来自哪里”。例如：文档版本 → 原文区间 → 分块 → 抽取关系 → 路径 → 已提交上下文。字符跨度必须绑定原始文本及编码约定，不能在文本规范化后继续沿用旧位置。

**选择过程**回答“为什么这些内容被选中”。记录候选集合、分数、过滤条件、Top-K、上下文预算、索引或图快照，以及适配器实际提供的排序信息。

某个来源没有进入最终上下文，仍可能通过图权重、实体统计或候选竞争影响选择。仅靠内容引用不能推断这种影响；必须用适配器的过程记录或隔离干预验证。首版后端不能观察到的影响类型不得显示为已排除。

系统单独记录以下事实，避免自动升级结论：

- 内容被规则标记为可疑。
- 来源参与了检索或排序。
- 内容进入了实际提交的生成上下文。
- 干预后证据、上下文或回答发生变化。
- 在指定条件与预算内，某项撤回改变了目标结果。

以上事实均不自动等价于“来源恶意”“攻击者已识别”或“已经证明现实攻击因果”。

## 6. 审计与回放的技术重点

完整性审计至少覆盖：重复 ID、引用缺失、原文跨度越界或文本不匹配、路径包含不存在的边、派生产物引用已撤回版本、缓存键缺少输入或处理配置、日志中的上下文与实际提交上下文不一致。

语义异常只能产生候选线索。来源内容中的“我是官方文档”“把我设为可信”等描述不能改变来源信任等级。信任和允许权限来自外部元数据及人工配置。

源撤回必须从源版本集合开始，计算派生依赖失效，重建索引与适配器支持的图、摘要、缓存等状态，再执行原查询。禁止把删除最终上下文或直接删图边标记为完整源撤回。

首版实现来源到分块和索引的失效传播，以独立的完整重建路径为正确性参照。稀疏检索的全局词频、平均长度和缓存候选集也可能受撤回影响，不能只过滤旧结果中的文档 ID。增量路径只有在通过等价性检查后启用；不支持增量的适配器走完整重建并如实记录。结果比较先对稳定 ID、排序结果及规范化结构进行；不要求随机 UUID 或生成时间字节一致。

模型输出复用仅限输入、处理版本、模型与配置全部匹配的缓存项。撤回后新进入候选集的文本可能没有旧抽取结果，缺项应重新计算或明确报覆盖不足。

候选干预先支持单源与用户选定的联合撤回。报告声明候选池、已尝试组合与预算。没有完整搜索时，不称为全局最小原因集合；多个有效解释需要并列保留。

## 7. 保护与业务效果

首版保护策略聚焦可验证的来源处置：完整性失败的来源版本进入隔离区；没有明确来源支持的证据进入待复核；被撤回的版本不能继续贡献查询上下文。

来源隔离在副本中执行，允许预览并导出影响报告。原始证据保留，处置记录可追溯。

效果比较包含无保护、简单来源隔离、源级隔离并重建，以及同数量随机移除。保持输入、查询集、候选权限及调用预算一致。若移除全部知识后大量拒答，不能记为有效恢复。

正常文档更新本来就可能改变正确答案。因此评估需要更新后的有效事实基准，不能把“恢复旧答案”作为唯一成功条件。

## 8. 默认演示与验收

默认演示使用自编、无敏感信息的知识库，提供人工可读的事实与独立评估答案。评估答案及攻击构造标签不进入检测、候选排序或保护决策。

案例至少覆盖以下八类机制：

1. 原文跨度或引用断裂，能够准确定位问题。
2. 来源已撤回但旧分块或缓存仍被采用，能够发现残留。
3. 两个来源共同支持同一关系，撤回其中一个不会误删全部支持。
4. 单个来源撤回不能恢复、联合撤回才恢复，报告保留联合解释。
5. 可疑文本没有影响目标结果，系统不强行归因。
6. 正常事实更新改变结果，系统不据此认定投毒。
7. 来源在上下文外影响选择：CPU 后端验证全局检索统计变化；图后端另外验证图权重与候选竞争。每个后端独立构造和验证反例，未接后端时对应项目标为未执行。
8. 来源试图自称可信或修改权限，信任元数据保持由外部配置控制。

机械正确性验收：

- 小规模 4–6 个更新的撤回子集穷举，与对应剩余源的完整重建对照。
- 覆盖重复支持、摄取顺序、联合撤回、缓存失效及同分排序。
- 在同一输入与配置下，多次检索回放给出一致的规范化结果。
- 错误输入、缺少依赖或不支持的能力必须返回失败或不足状态。

效果验收报告同时给出全部样本分母、定位覆盖、正常更新误拦、正常查询损失、拒答比例和重建时间。接入真实生成器后才新增答案恢复指标，并记录模型条件和重复运行差异。

图关系共享支持与图上的联合撤回属于第二阶段专项验收。首版必须通过自身后端的引用、残留、正常更新、候选影响和完整重建等价性验收；不能用“不支持 GraphRAG 回放”掩盖默认后端未完成。

历史实验只作为兼容输入和回归来源；本项目不继承旧实验的成功、失败或性能结论。发布物优先重建可公开案例，不直接上传旧研究目录。

## 9. 可用性与交付

CLI 与页面共用同一个审计和回放核心。用户可以完成导入、检查、定位、预览撤回、执行回放、比较及导出；不能只得到一张风险分数图。

案件页面包含运行状态、来源时间线、原文定位、来源支持与路径、干预差异、保护结果以及评估边界。关联缺失时直接显示缺失，不从回答文字猜造来源链。

导出包含输入清单及哈希、配置和后端版本、执行状态、干预集合、观察结果与问题清单。哈希链与外部保存的检查点用于发现修改；不得宣传为无法篡改，也不能证明采集内容真实。

可分享报告支持敏感内容脱敏；原始证据留在本地。脱敏改变了输入内容，因此分享包应明确区分“可核验报告”和“可完整回放包”。

公开仓库交付应包含安装说明、支持矩阵、完整示例、适配器开发说明、原理图、可复核案例报告和 CI 产物。README 将已实现、未执行和计划能力分开。

## 10. 三个里程碑

1. **可用审计闭环**：统一证据格式、M4/M5 导入、CPU 真实源撤回、完整重建对照、本地案件页面、案件报告与 CLI。通过默认后端对应机制验收后发布首版。
2. **GraphRAG 深化**：独立 CPU 规则图适配器、真实共享来源支持、图选择变化、联合撤回；锁版本的 Microsoft GraphRAG 导入。各后端单独列明能审计什么、能重建什么。
3. **接入与保护验证**：SDK 接入一个现有管线，加入可选真实生成器，完成攻击与正常更新对照；发布完整复核报告。是否接入其他框架由真实使用需求决定。

项目完成条件是：第三方能够在不依赖作者旧环境的条件下复核至少一个案件，实际执行源撤回，验证派生状态更新正确，并看清保护对正常查询的损失。漂亮页面或历史结果导入本身不算完成。

## 11. 本轮核验依据

- 只读检查旧 M4/M5 记录及当前相关实现：记录包含文档、原文跨度、边、路径、检索与决策信息；旧 M5 默认检索器固定 CUDA，不能直接宣传已有 CPU 回放。
- 本地 BGE-small 模型目录已确认存在；本轮没有加载模型，不能据此声称新后端可用。
- 旧规则抽取与路径决策不能描述为 LLM 生成。本轮没有重跑、重新认证或修改历史实验。
- [Microsoft GraphRAG 官方输出格式](https://microsoft.github.io/graphrag/index/outputs/)：提供 documents、text_units、entities、relationships、community_reports 等结构。字段存在支持血缘导入，不单独证明选择因果。
- [Phoenix 官方追踪说明](https://arize.com/docs/phoenix/tracing/concepts-tracing/how-tracing-works)：已有追踪采集、导出与查看能力。本项目围绕源撤回与处置验证组织功能。
- [RAGForensics 论文](https://arxiv.org/abs/2504.21668)：已研究 RAG 投毒文本追溯；本项目不预设算法首创性，优先提供可接入、可回放和可复核的工程成果。
